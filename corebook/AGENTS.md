# Forbidden Lands Corebook AGENTS

## Purpose

This file makes the `corebook/` folder self-contained inside the public `forbidden-lands-2e` repository.

If this manuscript is copied, shared, exported, or worked on outside the wider repository, this file must still give enough direction to preserve:

- the canonical status of the manuscript
- the integration policy for new rules
- the writing voice
- the structural rules style
- the table logic
- the editorial standard

Treat this file as the local master guide for work inside `corebook/`.

## Corebook Status

The files in this folder are the authoritative integrated manuscript for this Forbidden Lands 2E project.

That means:

- rules here are treated as canon
- text here should read as native rulebook prose
- no section should sound like patchwork from proposal notes
- no accepted rule should still be labeled as a variant unless the text truly intends it as optional play

## Manuscript Rule

When editing the corebook:

- write as though the rule always belonged in the book
- remove traces of old rule replacement language
- fold new rules into existing chapter logic and local cadence
- update nearby prose if the new rule changes assumptions around it

The reader should never feel the seam.

## Local Source Hierarchy

Inside `corebook/`, use this order:

1. explicit user instruction
2. this `AGENTS.md`
3. the already integrated surrounding manuscript text
4. `CHANGELOG.md` for implemented history
5. `../proposals/` only as support material
6. any external source text only to confirm inherited baseline, not to override accepted local canon without instruction

## Integration Policy

When a rule replaces or changes an earlier rule:

- never mention the replacement inside the final rules text
- never write "optional rule," "variant," "houserule," or "proposal" unless that status is intentionally visible in play
- rewrite surrounding text as needed so the rule sits naturally in the chapter

## Public Repo Caution

This manuscript is a public draft workbench.

Do not describe it as:

- official
- endorsed
- compliance-reviewed
- a legally cleared replacement corebook

Keep the public-facing notices in the repository root aligned with that reality.

## Core Style Standard

This manuscript must read like a professionally authored fantasy roleplaying corebook written by a master of both fiction and rules.

It must be:

- atmospheric
- stern
- practical
- readable at speed
- evocative without bloat
- consistent across chapters

It must not read like:

- a fan supplement
- software documentation in costume
- patch notes
- AI paraphrase
- wiki prose
- commentary about design intentions

## Authorial Voice

Write as an experienced tabletop writer with:

- deep familiarity with survival fantasy
- strong historical texture
- excellent rules pedagogy
- sharp editorial restraint
- respect for real table use

The voice should feel confident and lived-in.

## Tone

The book's default tone is:

- gritty
- practical
- dangerous
- quietly mythic
- survival-minded
- unsentimental
- serious about weather, wounds, hunger, and fear

Characters are not clean fantasy heroes. They are hard-used adventurers in a land full of ruins, rust, beasts, old magic, and bad odds.

## Register

Use plain, strong English with a low-tech fantasy edge.

Favor:

- short to medium sentences
- concrete nouns
- physical verbs
- practical imagery
- a slight archaic roughness

Avoid:

- modern slang
- breezy internet rhythm
- bureaucratic wording
- over-medical diction where a harsher field term works better
- decorative purple prose

## Audience Stance

Default stance is direct address to the table.

Use:

- second person for procedures and immediate instructions
- declarative prose for chapter framing and lore
- imperative rules language where clarity benefits

Good:

- "Roll `MOVE`."
- "If you fail, you fall."
- "The cold settles in your limbs."

Bad:

- "The intention here is that..."
- "This basically means..."

## Fiction Before Procedure

Open sections with one strong image or one hard statement of stakes when useful, then move into the rule quickly.

Do:

1. set the mood
2. define the trigger
3. explain the procedure
4. state the outcome and duration

Do not:

- spend three paragraphs warming up before the rule appears
- hide the actual mechanic inside flavor text

## Rules Clarity Standard

Every rule should answer:

1. when this happens
2. what the player or GM does
3. what is rolled, spent, or chosen
4. what the result is
5. how long it lasts
6. what can end, resist, alter, or override it

If the reader has to infer these from context, the passage is not done.

## Rule Sentence Forms

Prefer:

- "When X happens, do Y."
- "Roll `SKILL`."
- "If you fail, Z happens."
- "The effect lasts until dawn."
- "Treat it as broken."

Avoid:

- "It should be noted..."
- "In essence..."
- "This represents..."
- "The intention is..."

State the rule by effect.

## Mechanical Conventions

Use the manuscript's own game terms consistently:

- `Quarter Day`
- `Willpower`
- `Resource Die`
- `Broken`
- `NEAR`
- `FAR`
- `ARM'S LENGTH`
- `Strength`
- `Agility`
- `Wits`
- `Empathy`
- `HEALING`
- `SCOUTING`
- `MOVE`
- `MANIPULATION`
- `INSIGHT`

Do not drift into alternate labels once a canonical one exists.

## Formatting Conventions

- headings in title case
- dice notation as `D6`, `2D6`, `D66`
- uppercase for formal range bands and rules tags
- straight ASCII punctuation only
- markdown tables for structured outcomes and random results
- no "see page XX"
- named section references instead of vague references

## Chapter Fit

Before editing a section, read enough surrounding text to match:

- cadence
- density
- heading style
- degree of flavor
- mechanical compression

Do not write one chapter like a terse SRD and the next like a novel unless the local chapter already justifies that difference.

## Gear Writing

Gear text should imply:

- material
- use
- wear
- social place
- limitations

Cheap gear should feel cheap but necessary.
Specialized gear should feel specific, not generic.
Travel gear should feel hard-used, practical, and replaceable.

## Weapons And Armor

Weapon and armor writing should:

- respect real use where possible
- distinguish travel weapons from war weapons
- care about leverage, reach, weight, material, and handling
- avoid fantasy nonsense presented as realism

Some gear should feel brutal, clumsy, improvised, or provincial. Not everything should sound elegant.

## Magic

Magic is dangerous, unreliable, and often ugly.

Spell and mishap writing should feel:

- uncanny
- costly
- physical
- spiritually risky
- tactically consequential

Avoid polished high-fantasy sparkle language.

Magic should stain, twist, chill, attract, spoil, burn, exhaust, wake, warp, or reveal.

## Injuries

Injuries must match their actual mechanics.

That means:

- temporary injuries need temporary-sounding names
- permanent injuries need permanent-sounding names
- catastrophic injuries should sound catastrophic
- effects should feel bodily, low-tech, and credible

Prefer names someone in the setting might say over modern diagnostic labels.

## Horror

Horror writing should be authentic, severe, and behaviorally grounded.

Favor:

- dread
- numbness
- startle
- guilt
- dissociation
- collapse
- intrusive aftermath
- sleeplessness
- strained judgment

Avoid:

- joke phobias
- theatrical melodrama with no table value
- modern diagnostic exposition inside final rules prose

## Random Table Logic

Random tables must be dense, varied, and meaningful.

Avoid:

- too many filler rows
- endless self-damage repetition
- harmless joke outcomes in serious tables
- vague GM-fiat results with no usable boundary

Prefer:

- tactical trouble
- environmental fallout
- gear consequences
- social consequences
- delayed problems
- path-specific flavor
- escalating catastrophe at the top

## Catastrophe Standard

Catastrophic results must be:

- severe
- legible
- themed
- table-runnable

If a result is character-ending, write it as clearly character-ending.
If it is survivable, define the surviving condition.
Do not hide catastrophic meaning behind vague poetry.

## Realism Standard

Use realism to ground the game, not to bury it in simulation.

Good realism:

- names that match recovery times
- gear that wears out believably
- weather that matters
- travel labor that costs time and resources
- consequences that change player decisions

Bad realism:

- pedantry without play value
- clinical wording that breaks tone
- misery added only to sound serious

## Proposal Promotion Rule

If material from a proposal is integrated into `corebook/`:

- rewrite it fully into book voice
- remove rationale language
- adjust neighboring text
- update `CHANGELOG.md`

Never paste proposal prose straight into the manuscript and call it finished.

## Changelog Rule

`CHANGELOG.md` should record implemented manuscript changes, not speculative design work.

Entries should be:

- short
- specific
- player- or GM-readable
- mechanically accurate

## Workflow

Before editing:

1. identify the exact landing section
2. read enough local context
3. identify downstream chapter interactions
4. check whether the change is already staged in a proposal

During editing:

1. write in local cadence
2. integrate rather than append where possible
3. keep procedures explicit
4. preserve chapter identity

After editing:

1. update cross-references if needed
2. update `CHANGELOG.md` if canon changed
3. run markdown lint
4. reread the new text in place

## Hard Rules

- Do not leave integrated text sounding like a patch.
- Do not use modern casual language.
- Do not explain design rationale inside manuscript prose.
- Do not write vague mechanics when a bounded rule is possible.
- Do not contradict nearby text without resolving the contradiction.
- Do not forget surrounding consequences when a rule affects multiple chapters.

## Done Standard

Work in `corebook/` is done only when:

- the text fits the chapter
- the rule is clear
- the style matches the manuscript
- canon documentation is updated if needed
- markdown lint passes
- the passage no longer sounds imported from elsewhere
